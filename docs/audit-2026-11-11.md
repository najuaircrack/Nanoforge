# Nanoforge / Latticekin audit — 11 November 2026

Recommendation: focus Nanoforge on **helping a developer make a small, verified repository change with a capable local model, explicit approval, isolated tests, and an inspectable trace**.

The repository has useful foundations: a readable PyTorch transformer, data readers and tokenizers, training/checkpoints, inference adapters, retrieval primitives, a task suite, a studio and an early tool harness. Several supported paths currently produce incorrect results or fail before doing useful work. The main engineering problem is that configuration acceptance, registry names, completed jobs and passing smoke tests are being used as stronger evidence than they actually provide.

This audit covers the current working tree, including pre-existing uncommitted changes. Ten specialist agents reviewed the major subsystems. The parent reviewed their source evidence and independently reproduced selected high-risk defects. No production source fixes were made. Private datasets, checkpoints, facts and runtime reports were excluded. The findings are the defects discovered in these paths; further defects may remain.

## Additional parent findings: configuration validity

- **RC1 — P2:** load_config catches every YAML parsing exception and invokes its limited fallback parser. A syntactically broken document containing training.max_steps=7 and an unfinished bracket was accepted as a valid configuration. Catch missing-parser imports separately; reject malformed YAML with a located error. Source: config.py:253–261.
- **RC2 — P2:** unknown top-level sections are never checked or warned about. A document with trainng.max_steps=7 silently loaded the default training.max_steps=1000. Validate root keys and section types, and add a strict public validate-config mode. Source: config.py:263–268.

The fallback and root-key failures compound the existing section-key warning/ignore behavior. A configuration editor cannot promise full validation while these paths accept malformed or inert settings.

## What Nanoforge is doing wrong

1. **Training metrics can reward the wrong objective.** Current-token labels, leaked validation, missing completion masks, DPO padding and distillation masking can all yield attractive numbers without the intended behavior. Repair data supervision and evaluation before judging model quality.
2. **Accepted controls are often inert or approximate.** Quantization, attention backend choice, batch size, worker settings, some MoE controls and optimizer names do not consistently match their stated semantics. Each public control needs an enforced caller path and inspectable effective setting.
3. **Safety limits often limit waiting or display, rather than execution and allocation.** Threads continue after timeout, subprocess output is accumulated before truncation, and wall/token/byte accounting is incomplete. Define and enforce the actual boundary.
4. **The product loop is fragmented.** Import, Chat, training jobs, project manifests, approvals, observations and evaluation exist in separate partial paths. A user still cannot complete the charter's model-driven approved coding task through the console.
5. **Tests mostly prove presence and happy-path completion.** Shape checks, file existence, mounting a screen and parsing a GGUF container miss incorrect gradients, zero-update stages, inactive buttons and invalid model exports. Add parity, causality, negative-path and real interaction tests.
6. **Documentation is internally inconsistent.** Some target architecture paragraphs say supports while the backlog says planned. Some completed-phase language is stronger than the current artifacts and release evidence. Keep an explicit implemented/partial/planned table with callers and tests.

## Appendix — Model architecture and inference

Scope: model/, generation/, benchmark.py, config/registry contracts, documented callers, and existing tests. Source was not modified. Private runtime directories were not read. Severity uses P1 for defects that corrupt normal training/generation or substantial resource behavior; P2 for conditional features, incorrect configuration behavior, or validation failures.

### Confirmed defects

#### M1 — P1: gradient checkpointing silently computes gradients through the wrong block

- Evidence: src/nanoforge/model/transformer.py:126-131. The loop defines `_ckpt` with a free reference to `block`; checkpoint recomputation during backward sees the final loop block for earlier checkpoint functions.
- Public path: TrainConfig.gradient_checkpointing defaults to true (config.py:102); Trainer copies it onto the model (training/trainer.py:60). This affects normal multi-layer training.
- Reproduction: CPU torch 2.13.0, seed42, three layers/d_model32, dropout0, clone identical model, enable checkpointing only in clone, identical x/labels, compare q_proj.weight gradients. Forward loss was equal (5.5533480644); layer0 relative gradient difference 1.56343746, layer1 1.56637108, layer2 exactly equal.
- Impact: a plausible loss and successful training run can hide incorrect gradients and invalid comparisons.
- Fix: bind each block into the checkpoint function explicitly (e.g. per-block callable/default argument) and add a meaningful checkpoint-on/off gradient parity test.
- Confidence: dynamically confirmed. Existing tiny-forward/registry tests do not compare backward gradients.

#### M2 — P1: enabling checkpointing drops the MoE router auxiliary objective

- Evidence: transformer.py:128-132 discards `aux` and then sets it to None; heads.py:63-65 adds router loss only when auxiliary tensors survived the backbone.
- Reproduction: cloned two-layer, two-expert top_k1 model with seed43; checkpoint off aux_loss=2.0509119034, on aux_loss=None, otherwise same forward; total training loss differed by 0.0205092430.
- Impact: default checkpointed MoE training does not train the objective that config.router_aux_loss_coef promises.
- Fix: return/propagate router auxiliary outputs through checkpointing; test objective and router-gradient parity.
- Confidence: dynamically confirmed. Separate from M1 because binding the block alone does not restore aux_loss.

#### M3 — P1: rolling KV cache resets RoPE position after eviction

- Evidence: attention.py:180 computes past_len from retained key length; KVCache.append at :63-65 evicts older tokens without preserving a total processed-position counter.
- Reproduction: standalone attention, window4, fixed seven-token hidden input; compare full causal windowed attention to incremental cached attention. Differences stayed below 2e-7 through token4, then token5 max delta0.04265179 and token6 delta0.06151063. This first diverges on the second token after the cache fills because multiple new keys are assigned the same absolute RoPE position.
- Impact: decoding changes once a local window or max_seq_len is reached.
- Fix: track logical token positions separately from cache storage length; preserve them on clone and eviction. Test full/incremental parity across at least two evictions.
- Confidence: dynamically confirmed.

#### M4 — P1: capped prefill can attend to future tokens

- Evidence: attention.py:186-190 appends and truncates K/V before evaluating all prefill queries; _attention_mask at :95 aligns q_pos from kv_len-q_len, which becomes negative for early queries when prefill is longer than cache window. The finite-min fully masked row normalizes over retained future values.
- Reproduction: seven-token prefill/window4. Cached vs uncached first-query delta1.03406477 in one seed. Stronger causality check (seed44): mutate only the final input token; first query output changes0.59700352 with capped cache, versus0.0 without cache.
- Impact: cached prefill is not the same model as training; multiple layers can propagate these corrupted early representations into final-token predictions.
- Fix: evaluate queries against appropriate full/chunked K/V before evicting the cache for subsequent calls; use masks with valid absolute positions and a defined fully-masked-row behavior.
- Confidence: dynamically confirmed, including negative control.

#### M5 — P1: RoPE cache retains quadratic memory across generation lengths

- Evidence: rope.py:49 keys tables by the exact seq_len; :59 retains every complete table indefinitely. Decoding requests increasing lengths once per layer.
- Reproduction: RotaryEmbedding(dim64), request lengths1..256 on fp32 CPU. Retained tables total8,421,376 bytes; only longest table needs65,536 bytes, a128.5x ratio.
- Scaling: lengths1..2048 at head_dim64/fp32 require537,133,056 bytes per layer of retained cos/sin data, versus524,288 for one longest table. Eight such layers approach4GiB. This is an arithmetic projection of source allocation, not a measured8-layer run.
- Impact: CPU-first/local low-memory behavior can exhaust RAM despite a small model and bounded KV cache.
- Fix: maintain one growable maximum-length table per device/dtype/scaling identity and slice it; bound or evict tables. Recheck dynamic scaling separately because prefix positions may change with sequence length.
- Confidence: dynamically measured at256; larger figure derived explicitly. Existing profiling uses estimates and misses this actual retained-memory behavior.

#### M6 — P2: experimental sequence-mixing FFNs lack incremental state

- Evidence: moe.py:41-44 applies a temporal convolution only to the current x; :58-60 shifts only the current x. TransformerBlock caches only attention, not FFN state.
- Reproduction: compare final logits for seven-token full forward with six-token cached prefill plus one-token decode, same weights. rwkv_mixing max difference0.0015988573; mamba_selective_state0.0035598725.
- Impact: after prefill the generator runs these trained sequence mixers with missing previous-token context. Labeling them experimental is honest about architecture, but does not make this behavioral inconsistency safe.
- Fix: add bounded mixer/convolution state to the cache contract, or reject incremental caching for these FFNs and recompute enough context.
- Confidence: dynamically confirmed. Documentation already states these are not complete Mamba/RWKV architectures; that limitation alone is not counted as a bug.

#### M7 — P1: streaming corrupts valid multibyte UTF-8

- Evidence: engine.py:185-189 decodes a buffer and clears it whenever decode returns any text; ByteTokenizer.decode uses errors=replace (data/tokenizer.py:48-50), so an incomplete leading UTF-8 byte already produces nonempty replacement text.
- Reproduction: use the real ByteTokenizer to encode U+00E9, patch generate_ids to yield those exact two valid byte tokens. Full decode='é'; engine.complete='\uFFFD\uFFFD'.
- Impact: valid non-ASCII generated text is corrupted by stream/complete. The same algorithm can also mishandle tokenizer joins/spaces; only byte Unicode corruption was independently verified here.
- Fix: provide an incremental decoder/tokenizer-specific streaming contract that waits for complete bytes and emits only stable text; flush once at completion. Regression should compare stream concatenation with whole-token decode for Unicode.
- Confidence: dynamically confirmed with predetermined valid token output.

#### M8 — P2: exact prefix-cache hits duplicate the last prompt token

- Evidence: engine.py:90 sets pending_ids to empty when input exactly matches a stored prefix; the first iteration then uses :107 to feed ids[:,-1:] into an already complete prefix cache. PrefixCacheEntry stores no final prefill logits.
- Reproduction: cache_prefix('abc') with ByteTokenizer yields four prompt IDs including BOS. The next generate_ids call for exactly that prompt forwards only last ID103 with past cache length4, producing a logical five-token prompt.
- Impact: exact cache hits can change continuation semantics instead of saving the same computation.
- Fix: store final prefill logits with the prefix or cache all but the final prompt token. Test identical cached/uncached continuation including exact prefix and longer suffix.
- Confidence: dynamically confirmed through a forward spy.

#### M9 — P2: prompt truncation disables repetition penalties for generated output

- Evidence: engine.py:103 truncates the prompt to max_seq_len and :105 replaces ids with that suffix, but :113 starts history at len(input_ids), the original prompt length.
- Reproduction: original10 IDs/max_seq_len4/three generation steps; a sample_next spy sees [],[],[] instead of [],[new1],[new1,new2].
- Impact: no-repeat-ngram/frequency/presence/repetition penalties do not operate for the first original_length-retained_length generated tokens.
- Fix: track generated token history independently from cropped model input, with explicit prompt/generated boundaries.
- Confidence: dynamically confirmed.

#### M10 — P2: attention backend selection does not select the promised backend

- Evidence: registry.py:167-172 maps manual/sdpa/flash aliases to the same constructor; attention.py:134 and :194-199 route only by config.use_flash and global package availability, not attention_backend.
- Reproduction: ModelConfig(attention_backend='manual') with its default use_flash=True calls torch SDPA once; documented manual softmax path is not selected.
- Impact: experiments and diagnostics claiming a manual/SDPA backend can run another implementation; installing flash-attn can silently change all such configurations.
- Fix: separate backend selection from a generic optimization toggle; report actual selected kernel and fallback reasons.
- Confidence: dynamically confirmed for manual->SDPA routing. Real external FlashAttention was unavailable in this CPU environment.

#### M11 — P2: invalid cache-list length silently skips transformer layers

- Evidence: transformer.py:126 uses zip(self.blocks,caches) without exact cache-count validation.
- Reproduction: one-layer model called with caches=[] executes no block and still returns logits shape(1,3,260).
- Impact: an invalid public model API input produces plausible output from a different architecture instead of an inspectable failure.
- Fix: validate cache count/types/batch shapes before running blocks. Test too-short and too-long lists.
- Confidence: dynamically confirmed. Current GenerationEngine normally produces the right count; severity reflects malformed/external callers.

#### M12 — P2: unsupported RoPE scaling can silently pass instead of raising

- Evidence: rope.py:13-15 returns unscaled positions when factor<=1 before validating the scaling kind; configuration/architecture documentation says unsupported NTK raises.
- Reproduction: _scaled_positions(3,cpu,{'type':'ntk','factor':1}) returns [0,1,2].
- Impact: misspelled/unsupported scaling is silently ignored and run metadata does not describe an enforced configuration.
- Fix: validate kind, numeric range and required fields before early return. Test unsupported scaling with default/small factors.
- Confidence: dynamically confirmed.

#### M13 — P2: position='none' still requires an even RoPE head dimension

- Evidence: attention.py:160 constructs RotaryEmbedding unconditionally; rope.py:38 rejects odd dimensions, even when the forward will never use RoPE.
- Reproduction: valid divisibility config d_model3/n_heads1/position_embedding='none' passes ModelConfig then CausalSelfAttention raises 'RoPE head dimension must be even'.
- Impact: legal no-position/ALiBi configurations inherit an unrelated RoPE restriction.
- Fix: construct/validate RoPE only for the selected positional backend.
- Confidence: dynamically confirmed; low practical priority.

### Static concerns needing backend-specific validation

- attention.py:194 does not require x.device.type=='cuda' or a supported dtype before calling external flash_attn_func. Presence of the Python package alone causes a CPU/fp32 SDPA configuration to enter a CUDA-only kernel. No real flash-attn/CUDA run was available; this is a strong static routing defect, not a measured external-kernel failure.
- attention.py:198 sends causal=False whenever cached kv_len differs from the new seq_len and supplies no window_size. A cached multi-token suffix therefore has no causal mask in the external kernel, and configured sliding_window is ignored. Single-token decode causal=False is fine when all retained keys precede the query; multi-token cached suffixes need a bottom-right aligned causal mask. Requires actual kernel parity/causality testing.
- config.py:20/docs/configuration.md:176 advertise capacity_factor as an expert capacity multiplier. moe.py never reads it or enforces token capacity. This is an unenforced config/claim, not evidence that unbounded execution always fails.
- benchmark.py does not validate steps>0, accepts a model config whose data.seq_len may exceed model.max_seq_len, and reports an analytic profile alongside measured throughput. Inference latency, resident/peak process memory, retained RoPE cache and task quality remain separate unmet product measurements.

### Honest capability boundaries and next work

GQA/MQA, dense attention, rotary/ALiBi, tied embeddings, dense FFNs and contiguous KV caches are real. ### Verified and source-proven coding defects

#### T1 — High: every distributed rank writes the same checkpoint and manifest paths
Evidence: src/nanoforge/training/trainer.py:59 sets is_main_process, but no later writer checks it. RunManifestWriter is initialized at :83, resetting metric logger at :113, all checkpoint calls at :360/:474/:489/:504, and completion manifest at :522 execute on every rank. src/nanoforge/training/checkpoint.py:105 uses the same path.pt.tmp, then :107 replaces the common checkpoint. Non-main-rank synthetic run wrote last.pt with is_main=False.
Mechanism/impact: ranks can truncate/move each other's metrics, race atomic temporary checkpoint names, overwrite sidecars, or observe an inconsistent checkpoint/hash pair. The process-level file replacement is not a distributed write protocol.
Fix: rank-zero-only persistent outputs for DDP; collective FSDP state gathering with an explicit supported state-dict/optimizer-state protocol before rank-zero saving; barrier and agreed failure handling where needed. Add a two-process Gloo test checking that only rank zero writes and a standalone loader can open the checkpoint.
Confidence: high; real cross-rank race not executed. Existing four focused tests are single-process and do not cover this.

#### T2 — High: DDP ranks draw duplicate data, so extra processes do not increase effective batch diversity
Evidence: trainer.py:52 calls seed_everything(config.training.seed) identically on every rank, before model construction. Rank is not used in data sampling. _batch at :182 uses PackedMemmapDataset.sample, whose data/dataset.py:88 uses global NumPy RNG. Resetting the same seed before sampling yielded identical batches.
Mechanism/impact: synchronized DDP computes the same gradients repeatedly instead of processing disjoint microbatches; the advertised scale-out advantage and world-size batch interpretation are misleading. Dataset mixtures also have only the same configured seed.
Fix: keep model initialization consistent, then give each rank deterministic disjoint sampling/sharding and save rank-specific sampler/RNG state. Include world_size in effective batch/token accounting. Verify sample identities across two real CPU ranks.
Confidence: high from source and sampler reproduction; no actual DDP launch.

#### T3 — High: checkpoint step semantics skip work on resume
Evidence: trainer.py:178 resumes checkpoint.step + 1. Interrupt saves the upcoming, unexecuted loop step at :355-:365; normal completion saves max_steps at :509 although the last executed zero-based step is max_steps - 1.
Reproduction: after one completed update, interrupt.pt stores 1 and resume starts 2 instead of 1. After three completed updates, last.pt stores 3 and resume starts 4 instead of 3.
Impact: interrupted/resumed training is not equivalent to uninterrupted training; schedule steps and training budget are skipped. Extending a completed run also loses an update.
Fix: use an explicit completed_updates or next_step counter consistently, document/migrate existing schema semantics, and test uninterrupted versus checkpoint-resumed weights/RNG/batches.
Confidence: runtime-confirmed. Existing shutdown test asserts checkpoint existence and final_step bounds but never resumes it.

#### T4 — High: early stopping falsely records full max_steps and prevents legitimate continuation
Evidence: trainer.py:485 breaks the loop when stale, then :502 sets final_step=max_steps whenever not interrupted; :509 saves max_steps, and :524 records it.
Reproduction: max_steps=8, eval_interval=1, patience=1 and constant validation loss perform exactly three optimizer updates, while last.pt and run.manifest.json report final_step=8.
Impact: resource/quality reports overclaim work performed; resume believes the full schedule completed and can run zero further updates.
Fix: preserve actual completed updates and termination reason (early_stopped vs max_steps vs cancelled), and save that counter. Test early-stop checkpoint and manifest counters together.
Confidence: runtime-confirmed; not covered by current tests.

#### T5 — Medium: resume restores neither EMA nor the full training selection/scaler state
Evidence: EMA is constructed from fresh random weights at trainer.py:79, before _resume. _resume at :169-:180 loads model/optimizer/RNG only. Saved EMA exists in checkpoint payload but is ignored. best_val and stale_evals reset at :310-:313. GradScaler state is absent from checkpoint.py:86-:99.
Reproduction: all 11 saved EMA tensors differ from resumed EMA tensors on the tiny fixture. A worse validation value after resume is automatically treated as a new best because best_val returns to infinity.
Impact: resumed EMA trajectories are wrong; best.pt can be overwritten by a worse model; early-stop patience resets; fp16 loss scaling is not continuous.
Fix: save/restore EMA, scaler, best validation loss, stale-evaluation count and precise step state; tolerate old artifacts explicitly. Test continuity and preservation of a historical best checkpoint.
Confidence: EMA runtime-confirmed; best/scaler source-proven; fp16 not executed.

#### T6 — High: failure paths do not restore signal handlers or finish the real CLI run manifest
Evidence: Trainer.train installs handlers at :299-:308 and restores them only after success at :526. There is no enclosing try/finally; AsyncCheckpointSaver.close at :513 is also success-only. train_from_config has a failure-manifest catch at :543-:547, but run_training_with_optional_tui's noninteractive/no-TUI paths at :567-:576 call Trainer(cfg).train directly, and the TUI worker at :582 only records an error in process memory.
Reproduction: an injected RuntimeError in _forward_loss leaves both SIGINT/SIGTERM handlers changed and manifest status running.
Impact: failed jobs can appear active forever; handlers keep references to stale trainers; async save/thread and logging resources have no guaranteed cleanup.
Fix: put finalization in Trainer-level try/except/finally used by every caller, record failed status and termination reason, wait/close saver safely without hiding the original error, restore handlers and close TensorBoard/W&B.
Confidence: runtime-confirmed handler/manifest behavior, actual CLI path traced. Four focused tests exercise only successful and cooperative-stop flows.

#### T7 — Medium: resumed throughput is inflated by counting historical tokens against only current elapsed time
Evidence: trainer.py:314 resets t0; :436 computes toks=(step+1)*tokens_per_step, then :441 divides that cumulative counter by elapsed since the current train() call.
Mechanism: resuming at step 10,000 makes the first current-session metric include roughly 10,001 steps of tokens against one step of wall time. Skipped optimizer steps also count full token budget even if a nonfinite first microbatch aborts accumulation.
Impact: CPU/GPU throughput comparisons and run resource reports are false.
Fix: separately track lifetime tokens and session processed tokens, count actually processed valid tokens, and divide session work by session elapsed time. Include world size for unique global tokens.
Confidence: source-proven; no numeric performance experiment needed.

#### T8 — Medium: checkpoint manifests overcount parameters with tied embeddings
Evidence: checkpoint.py:132 sums all model.state_dict values rather than unique parameters. Tied lm_head/embedding appear as two state-dict entries.
Reproduction: tiny tied-embedding model has 3,600 parameters, while checkpoint-manifest formula returns 4,112 (512 duplicate embedding elements).
Impact: artifact model size/resource provenance disagrees with the correct training run parameter count.
Fix: compute unique model parameters before serialization and carry that number into metadata; distinguish buffers and stored tensor elements. Add tied/untied model manifest tests.
Confidence: runtime-confirmed formula; manifest artifact writer belongs to evaluation reviewer too.

#### T9 — Medium: Adafactor's factored second-moment normalization is mathematically wrong
Evidence: training/optimizers.py:74-:76 reconstructs denominator as sqrt(row) * sqrt(col), omitting normalization by the mean row statistic. The factored estimate should reconstruct outer(row,col)/mean(row) before taking its square root.
Reproduction: direct public Adafactor on a constant 2x2 gradient of 10, lr=1, beta2=0 produces an update of -0.1 rather than the normalized/clipped factored update -1.0. The source permits beta2=0; the defect also changes behavior as default-EMA statistics converge.
Impact: matrix updates use an incorrect, gradient-scale-dependent preconditioner. Norm clipping can mask the difference in some inputs, making smoke tests insufficient.
Fix: implement/reference-check the complete factored estimator and clearly describe any intentionally simplified algorithm. Use analytic matrix fixtures and comparison against a trusted Adafactor implementation.
Confidence: analytic source proof plus runtime-confirmed current result; no optimizer equivalence tests found.

#### T10 — Medium: masked-gradient accumulation does not equal one effective token batch
Evidence: trainer.py:383 divides each microbatch's already-averaged loss by grad_accum_steps; model heads use cross_entropy(ignore_index=-100) with mean reduction. Different assistant-label counts get equal microbatch weights.
Example: a one-valid-token microbatch and a 100-valid-token microbatch each contribute 50% with accumulation=2, while a concatenated token-mean loss weights them 1/101 and 100/101.
Impact: assistant-only/FIM training changes objective when micro_batch_size or accumulation changes; the nominal effective batch semantics are not stable.
Fix: explicitly choose/document sample-mean versus valid-token-mean objective; for token mean, accumulate summed loss normalized by total valid labels across the effective batch, including DDP reductions. Add a gradient comparison with uneven mask counts.
Confidence: source/analytic proof; public docs imply optimizer effective batch rather than an explicitly different sample-weighted objective.

### Static concerns requiring hardware or product decisions

- GPU gradient norm/device handling: utils.py:70 creates the accumulator on CPU, then :77 adds device-local sums. Review/verify CUDA and MPS behavior; place the accumulator on the gradient device and reduce there. No GPU existed in the audit environment, so this is not claimed as a confirmed runtime crash.
- fp16 grad_clip=0 metrics: trainer.py:396 only unscales before norm when grad_clip>0. The else branch :405 measures scaled gradients, although scaler.step later unscales them. This yields inconsistent norm/health metrics. A CUDA test should compare clipped-disabled/enabled norm observations.
- FSDP checkpointing is explicitly acknowledged incomplete in platform-audit.md:191. distributed.py:151 documents the missing consolidation but inaccurately says default FSDP state_dict is necessarily local-sharded; actual defaults depend on PyTorch state-dict mode. The trainer calls an unwrapped root containing FSDP-wrapped children; this is not a portable checkpoint API. Do not advertise production FSDP recovery until full-state and optimizer-state roundtrip tests pass.
- DDP lacks no_sync during intermediate accumulation (:379-:389), an acknowledged performance limitation, not a mathematical bug.
- configured training.batch_size and data.num_workers have no control over this sampler; effective batch is micro_batch_size * grad_accum_steps (and should account for unique rank data). Config metadata should reject conflicts or derive the value.
- evaluation is sampled from the same global NumPy RNG as training and not a persisted fixed validation-case set. Changing eval frequency changes subsequent training windows. This is deterministic under an exact config but limits fair comparisons.
- health metrics do not implement attention entropy, activation saturation, dead channels or NaN source analysis from the roadmap. These are unfinished work, not existing diagnostics.
- async saver clones every tensor to CPU synchronously before its write worker. It overlaps serialization, not GPU-to-host state capture, and increases snapshot RAM. Performance claims require measurements.

### Inaccurate or incomplete public claims

1. docs/architecture.md:221-:222 says AdamW, Lion, Adafactor and Sophia-G are all real implementations. SophiaG's own docstring at optimizers.py:89 calls it a scaffold; :120 updates h from gradient squared, not a Sophia-G Hessian-estimation procedure. Mark it experimental/simplified, and fix Adafactor normalization before asserting equivalence.
2. docs/configuration.md:211 repeats all implemented. Registry availability is different from algorithm fidelity.
3. docs/configuration.md:106 says distributed is single-process today, while distributed.py implements DDP/FSDP wrappers. The truthful description is DDP code exists but data and persistence correctness need hardening, and FSDP recovery is unsupported/unverified.
4. docs/architecture.md:228 describes saved EMA state; saved presence is real, resumed use is absent. Resume guarantees should say exactly which states are restored.
5. The four existing focused tests all pass but do not test true resume equivalence, early stopping, exception finalization, masked-accumulation equivalence, optimizer fidelity or distributed file ownership.

### Recommended training work sequence

First repair update counters, resume state, early-stop accounting and guaranteed finalization with focused regression cases. Then make rank-zero persistence and rank-specific deterministic data part of a tested two-process CPU/DDP slice. Keep FSDP unsupported until a full checkpoint/optimizer roundtrip exists. Add honest unique-parameter/token/time accounting. Prefer the well-tested AdamW path over adding more optimizer names; verify Adafactor before promoting it. Preserve CPU scratch training as a smoke/research tool rather than using its decreasing loss as evidence of coding-agent capability.

## Appendix — Data ingestion, packing and tokenizers

Scope: current worktree, read-only source review of data modules, CLI callers, config and focused tests. Private `data/`, `models/`, `runs/`, and `reports/` were not inspected. P1 means a supported path produces wrong supervision, corrupts a dataset, blocks operation, or contaminates evaluation. P2 means important correctness, reproducibility or scaling failure. Runtime-confirmed findings use synthetic fixtures.

### Findings

#### D01 — P1 — Generic batch tokenizer assumes a native-only private attribute

**Evidence:** `src/nanoforge/data/native_tokenizer.py:257` and `:263` read `self._native` in the exported module-level `encode_batch(tokenizer, texts)`. `ByteTokenizer`, `PurePythonBPETokenizer`, Hugging Face BPE/WordPiece and SentencePiece adapters do not declare that attribute. Callers are `packing.py:147` and `tokenizer_benchmark.py:92`.

**Runtime:** `encode_batch(ByteTokenizer(), ['synthetic example'])` and the same call with `PurePythonBPETokenizer()` both raise `AttributeError`. Plain generative/code preparation takes this batch path whenever tokenizer_batch_size > 1. Default auto boundary packing avoids it, which helps explain why current tests miss the failure.

**Impact/fix:** supported fallback tokenizers cannot prepare plain datasets or run the generic benchmark. Dispatch through the public optional `encode_batch` method or fall back to `encode`, rather than accessing private native state. Confidence: high. Existing tests benchmark only the NativeByteTokenizer facade.

#### D02 — P1 — Non-boundary label shards train copying the current input

**Evidence:** `packing.py:205` writes labels when loss_masking is auto or partial. These labels are unshifted for non-boundary packing (`packing.py:201` declares labels_are_shifted false). `dataset.py:90` always slices labels at the input index; it never reads labels_are_shifted.

**Runtime:** synthetic `mode='generative', loss_masking='auto', tokenizer_batch_size=1, seq_len=16` yielded four sampled rows with `x == y` for 100% of tokens. Normal next-token supervision requires the next token, rather than the visible current token.

**Impact/fix:** loss can approach zero through copying while generation remains poor. Honor the manifest shift contract: non-shifted labels must be sliced at i+1, fixed pre-shifted labels at i. Add direct token-alignment tests for generative auto/partial masking. Confidence: high. Existing tests verify only fixed masked chat.

#### D03 — P1 — Fixed sequences are split at arbitrary shard boundaries

**Evidence:** `packing.py:64` flushes after every shard_tokens tokens regardless of fixed sequence length. `dataset.py:74` and `:79` assume each shard begins at a fixed-sequence boundary. Default shard_tokens is 50,000,000; this is not divisible by the default 512 sequence length (remainder 128).

**Runtime:** seq_len=16, shard_tokens=17 packed four sequences. Loader reported three, using shard lengths [17,17,17] and discarding the last 13-token shard. Its second and later shards start in the middle of an original sequence.

**Impact/fix:** large datasets lose sequence boundaries, masks/context alignments and tail examples. Flush complete sequences together, require aligned shard sizes, or save absolute offsets and reconstruct across shards. Confidence: high. Current tests stay below a shard boundary.

#### D04 — P1 — Missing label shards silently disable supervised masking

**Evidence:** `dataset.py:38` and `:45` omit missing token/label files rather than validating the manifest. When shard counts differ, `:46` leaves labels unset. Mismatched lengths also silently drop entire shards (`:54`).

**Runtime:** deleting a synthetic fixed dataset's only label file still allowed construction with `labels is None`; sampling produced x shape [1,16] and y shape [1,15]. On larger shards, fallback next-token labels can cross a packed conversation boundary and train prompt/padding tokens.

**Impact/fix:** partial copies/interrupted outputs silently change the objective or later fail with opaque shape errors. Require all listed shards, aligned token/label lengths, fixed-sequence divisibility and explicit label policy. Confidence: high. No malformed/missing-shard regression found.

#### D05 — P1 — Validation is not reliably held out

**Evidence:** `packing.py:257` chooses train/validation separately for every sequence of a record, after splitting responses/FIM documents into sequences. `:300` copies the first training sequence into validation when validation is empty, including val_fraction=0; `:305` performs the inverse when training is empty.

**Runtime:** val_fraction=0 still produced 16 validation tokens identical to the first 16 training tokens. A single long record supplies validation through its first sequence and training through later sequences.

**Impact/fix:** held-out loss can measure duplicated context/documents or identical training examples. Assign a split once per source record/group before expanding sequences. For an insufficient split, fail or explicitly label a smoke-only overlapping split; respect val_fraction=0. Persist split IDs and seed. Confidence: high. `test_fim_packing_reserves_a_loadable_validation_sequence` checks nonempty splits rather than independence.

#### D06 — P1 — Prompt/completion rows lose their supervision boundary

**Evidence:** `formats.py:292` simply joins prompt and completion/response with a newline. It tags them completion mode. `modes.py:298` recognizes only role markers or specific response headings; `:306` silently falls back to all-token labels when no marker exists.

**Runtime:** a synthetic 26-character prompt plus completion was labeled completion_only, but only BOS was masked (one masked token), and the entire prompt was trained.

**Impact/fix:** common instruction data receives the wrong loss despite metadata claiming completion-only. Carry separate prompt/completion fields or emit a canonical boundary; reject an unparseable requested mask. Confidence: high. Existing tests exercise role-marked chat rather than plain prompt/completion.

#### D07 — P1 — The FIM transform uses a preceding span as the suffix

**Evidence:** `fim.py:36` sets suffix to the beginning of remainder, while `:37` sets middle to its final tail. Source order is therefore prefix+suffix+middle, not prefix+middle+suffix.

**Runtime:** abcdefgh becomes prefix abcd, suffix ef, middle gh. The model predicts the tail gh from two preceding spans; no future suffix follows the missing span in the source.

**Impact/fix:** the declared fill-in-the-middle objective teaches a reordered prefix completion instead of filling an internal gap. Choose two cut positions and define prefix=text[:a], middle=text[a:b], suffix=text[b:]. Test reconstruction using prefix+middle+suffix and a nonempty future suffix. Confidence: high. `tests/test_fim.py:10` currently asserts the incorrect ordering.

#### D08 — P2 — FIM special tokens disagree across formatting and tokenizers

**Evidence:** `fim.py:19` uses <|fim_prefix|>, <|fim_suffix|>, <|fim_middle|>. `tokenizer.py:107`, BPE trainer special list (`:314`), SentencePiece user-defined symbols (`:540`) and native `lib.rs:19` reserve names without the pipes. In addition, PurePythonBPETokenizer.encode (`tokenizer.py:142`) and native BPE encode (`lib.rs:533`) always start from ordinary bytes, so even their listed special literal tokens are never recognized as single IDs.

**Runtime:** PurePythonBPETokenizer encodes <|fim_prefix|> into 14 ordinary byte IDs; reserved ID 4 corresponds to the different literal <fim_prefix> and is not emitted.

**Impact/fix:** bundled real-training paths do not meet FIM's documented dedicated-sentinel requirement. Unify token names and implement special-literal recognition/validation, including save/load and native parity. Confidence: high for Python, source-confirmed for Rust. Existing FIM tests use the intentionally smoke-only byte tokenizer.

#### D09 — P2 — Detected speaker/text message schemas are serialized empty

**Evidence:** `formats.py:346` accepts role/from/speaker and content/value/text/message as message dictionaries. `formats.py:425` and `:430` serialize only role/from and content/value.

**Runtime:** two synthetic turns with speaker and text became '<|user|>\\n\\n<|user|>\\n', marked chat mode. Content and the assistant role disappeared.

**Impact/fix:** advertised shape-aware ingestion can train empty conversations or all-masked examples. Use the same role/content accessors for shape detection and serialization and count invalid roles/content. Confidence: high. Tests cover role/content and from/value, not the accepted alternatives.

#### D10 — P2 — Missing tokenizer paths silently switch to bytes, even for invalid names

**Evidence:** `tokenizer.py:263` returns ByteTokenizer whenever path is None before checking nonbyte types or validity.

**Runtime:** load_tokenizer('bpe'), load_tokenizer('native-bpe'), load_tokenizer('sentencepiece') and load_tokenizer('invalid-kind') all returned ByteTokenizer without a warning.

**Impact/fix:** a requested quality tokenizer can silently become the smoke tokenizer and mismatch an existing model vocabulary/encoding. Require a path for artifact-based tokenizers and validate the type before choosing a default. Confidence: high. Public callers: prepare CLI, generation/import/config workflows.

#### D11 — P2 — Boundary chat packing discards history and continuation context

**Evidence:** `modes.py:179` collects every system message globally; `:189` builds each answer's prefix from only the last system and last user, omitting previous assistant/user history. `:198` restarts every long-answer chunk from the same prefix, omitting preceding answer tokens. A later system message can also be applied to an earlier answer.

**Runtime:** a synthetic long answer split into sequences beginning with the same assistant marker, followed by 'FIRSTANSWER SECO', then 'NDANSWER THIRDAN', then 'SWER'. These latter chunks are trained as independent first responses with no continuation.

**Impact/fix:** conversational dependencies and long-answer coherence are not preserved. Build causal history only from earlier turns and include continuation context with an explicit truncation policy and counts. Confidence: high. Current docs describe repeated context prefixes, but do not explain that preceding answer/history is lost; no multi-turn/continuation regression found.

#### D12 — P2 — Optional Rust cleaning changes dataset semantics

**Evidence:** Python min_chars uses Unicode character count (`cleaning.py:115`), Rust uses UTF-8 byte count (`cleaning.rs:212`). Python truncates max_chars before exact dedup (`cleaning.py:117`, `:122`); native deduplicates first and the Python facade truncates afterward (`cleaning.py:89`, `:93`). Python simhash uses BLAKE2b (`cleaning.py:45`), Rust uses FNV-1a (`cleaning.rs:81`).

**Source controls:** '界界界\\n' has four characters and ten UTF-8 bytes, so min_chars=8 produces different retention. Two different long strings sharing the first max_chars become duplicates only in Python. Different hash functions do not guarantee identical near-duplicate decisions.

**Impact/fix:** merely installing optional acceleration changes filtering counts and train/validation contents, despite `cleaning.rs:5` claiming an identical fallback. Define one common algorithm/order/length unit and cross-language golden fixtures. Confidence: high from source; Rust extension unavailable locally, so native execution was not claimed.

#### D13 — P2 — Streaming and memory reports stop before the memory-heavy work

**Evidence:** plain files use read_bytes (`formats.py:247`), HTTP uses unbounded response.read (`:747`), archives read full members (`:691`, `:709`), JSON/YAML/XML parse full documents. Python BPE stores a list of Python integers for every corpus byte (`tokenizer.py:361`, `:365`) and rebuilds all sequences each merge. _scan_training_texts stops tracemalloc before fitting (`:567`), yet returns peak_memory_mb as the tokenizer training report. Native training spools text but holds a unique-word corpus in memory.

**Impact/fix:** a local low-RAM user can OOM while a report shows only a low inspection peak. Expose true fitting/packing peaks, explicit resource bounds, streaming text/HTTP/member processing and a disk-backed or capped fallback. Confidence: high static source. Documented Python fallback is real but is not low-memory tokenizer training. `data/profiler.py:10` claims nothing loads a full corpus, though it delegates to whole-file readers.

#### D14 — P2 — Packing provenance cannot reproduce or validate its split

**Evidence:** packing.manifest.json (`packing.py:317`) lacks schema version, split seed/fraction, tokenizer identity/fingerprint, cleaning policy and filtering counters; it records PID instead. DatasetStats.records/bytes_read are incremented by inspect_dataset, not the iterator used in packing. `formats.py:198` fingerprints resolved path+size+mtime instead of content.

**Runtime:** one successfully packed synthetic record had dataset.records=0 and bytes_read=0; seed and tokenizer identity were absent. Two identical-content files had different fingerprints.

**Impact/fix:** manifests cannot prove identical input content, identify filtering or reproduce partitions; the declared duplicate-dataset fingerprint is location-dependent. Record versioned content fingerprints, tokenizer artifact identity, seed, fraction, grouped split IDs, cleaning/filter counts and accurate record/byte counters. Confidence: high. Existing artifact tests do not validate this packing manifest contract.

#### D15 — P2 — Ordinary gzip text/JSONL is detected but cannot be ingested

**Evidence:** `formats.py:103` categorizes every .gz as archive; `:697` sends nonzip archives to tarfile.open.

**Runtime:** synthetic plain.jsonl.gz containing one valid JSONL record yielded zero records and a tarfile ReadError. A gzip text/JSONL stream is not a tar archive.

**Impact/fix:** common compressed datasets accepted by detection disappear from training with an archive issue. Distinguish gzip-compressed text/JSONL from tar.gz and stream decompression to the correct reader. Confidence: high. Existing archives tests do not cover plain gzip.

#### D16 — P2 — Fixed chunk stride silently omits next-token transitions

**Evidence:** `modes.py:263` sets chunk_width=seq_len+1 and `:264` advances by that width, then `:276` drops the first label of each chunk.

**Source proof:** with seq_len=4 and token IDs 0..9, target chunks cover 1..4 and 6..9; target 5, the token after the preceding chunk's last token, never participates. A one-token tail is discarded.

**Impact/fix:** each chunk boundary loses one supervised transition without a reported count. Advance by seq_len with a one-token overlap or persist intentional dropped-target statistics and policy. Confidence: high source. Current tests do not verify complete transition coverage.

## Appendix — Agent protocol, executor and safety

Read-only current-worktree review. Sources: agent/protocol.py, executor.py, harness.py, actions.py, provider.py, project.py, repository.py, tools.py; tests/test_agent_harness.py and tests/test_agent_project.py; agent architecture and relevant platform-audit sections. All probes used synthetic in-memory values. No private runtime files inspected. Source callers and tests were reviewed before failure-case probes.

### Confirmed coding defects

#### A1 — High: a timed-out or cancelled tool continues running

- Location: `src/nanoforge/agent/executor.py:132` through 139; `protocol.py:129`.
- Mechanism: `future.result(timeout=...)` only stops waiting; `shutdown(wait=False, cancel_futures=True)` cannot cancel a running thread. The executor neither passes the cancellation token to the callable nor polls it while waiting, and performs no cancellation check after completion.
- Synthetic verification: tool sleeps 60 ms then appends to an in-memory list, with a 10 ms timeout. Executor returns `timeout` with an empty list; later the list contains `late-effect`. Separate 50 ms tool cancelled after 10 ms returns `ok` with cancellation set.
- Impact: an approved write/test can execute after the operator sees timeout/cancellation; stuck worker threads also survive the tool result and can prevent interpreter shutdown. Repository test tool's 30-second outer timeout versus 60-second internal default makes this reachable, as workspace reviewer independently observed.
- Fix: isolate side-effectful tools in cancellable processes with process-group cleanup, propagate token/deadline, and explicitly distinguish a timed-out wait from confirmed stopped execution. Add delayed-effect and cancellation tests.
- Confidence: verified. Existing tests cover pre-action policy and step limits, not active interruption. Hard OS isolation is explicitly unfinished, but the current timeout/cancellation behavior still needs honest status semantics.

#### A2 — High: wall-clock budget does not bound provider execution or the final result

- Location: `src/nanoforge/agent/harness.py:74`, 79, 121, 133, 136; `protocol.py:104` and 111.
- Mechanism: wall time is checked only before an iteration. Provider execution is synchronous with no remaining deadline. A final action is returned without a new wall-clock/cancellation check. Direct ToolExecutor calls check only call count, so an already expired wall budget also does not prevent a tool invocation.
- Synthetic verification: legacy provider sleeps 40 ms then emits a final action with `ExecutionBudget(max_wall_seconds=.01)`; run returns `completed` after approximately 47 ms, exceeding its 10 ms limit. A non-returning provider has no executor timeout at all.
- Impact: a run advertised as bounded can hang or finish successfully after its resource policy expires.
- Fix: calculate a remaining deadline for each provider/tool call, use cooperative/isolated interruption, and recheck wall time/cancellation before accepting results and finals.
- Confidence: verified; no deadline-overrun test in inspected harness tests.

#### A3 — Medium: configured run output limit is ignored

- Location: `src/nanoforge/agent/executor.py:138`; `protocol.py:99`; `harness.py:85` and 146.
- Mechanism: tool output is bounded only by `spec.max_output_bytes`; `budget.max_output_bytes` never constrains tool observations. It is incorrectly reused as a cap on provider token count instead. Errors/final answers also have no consistent run byte-budget enforcement.
- Synthetic verification: budget 8 bytes, tool limit 10,000 bytes, tool returns 100 ASCII characters; result serializes to 102 bytes with `truncated=False`.
- Impact: a project manifest's lower output limit does not control observations/context growth.
- Fix: define per-result versus cumulative budget semantics, apply the smaller tool/run allowance, account UTF-8 bytes and errors, and introduce a separate token budget.
- Confidence: verified; current tests exercise step budget only.

#### A4 — Medium: byte truncation counts characters and may return unchanged oversized content

- Location: `src/nanoforge/agent/protocol.py:18` through 22 and 85 through 90.
- Mechanism: `bounded()` detects oversize in UTF-8 bytes but `_bounded()` tests/slices Python characters. Added truncation metadata is also outside the allowance.
- Synthetic verification: 100 euro signs with a 100-byte tool limit produce a 302-byte JSON string. `truncated=True` even though output is unchanged.
- Impact: multibyte text violates the advertised limit and truncation metadata is misleading.
- Fix: truncate at a valid UTF-8 boundary while reserving serialization/metadata overhead, then assert encoded final output fits its allowance.
- Confidence: verified; absent Unicode limit regression.

#### A5 — Medium: policy-required approval can be skipped

- Location: `src/nanoforge/agent/executor.py:123` through 129; `protocol.py:138`.
- Mechanism: `PolicyDecision.requires_approval` is considered only when `allowed=False`. An extension policy returning `allowed=True, requires_approval=True` executes without consulting the approval provider unless the tool itself has `approval_policy='always'`.
- Synthetic verification: policy returns `PolicyDecision(True, 'confirmation required', True)` for an echo tool with default approval policy; default DenyApproval is bypassed and result is `ok`.
- Impact: a policy extension's explicit approval requirement is lost. The built-in AllowReadOnlyPolicy does not currently use this combination, so this is an extension-boundary defect rather than a demonstrated default-policy escape.
- Fix: either enforce approval whenever the flag is true or validate/reject contradictory PolicyDecision states and document the invariant. Test the flag independently of tool metadata.
- Confidence: verified public-protocol behavior.

#### A6 — Medium: advertised tool schemas silently ignore safety constraints

- Location: `src/nanoforge/agent/executor.py:23` through 61 and 70.
- Mechanism: validator checks object fields and primitive types but ignores `enum`, `minimum`, `maximum`, array `items`, string lengths/patterns and unknown types/keywords. Registration does not reject unsupported schema features.
- Synthetic verification: integer schema with minimum 1, maximum 5, enum [1,2] accepts 99 and invokes the tool successfully.
- Impact: a tool author can believe constraints visible in the exposed schema are enforced when they are not. Built-in tools provide some extra validation, but arbitrary registered tools lack that safeguard.
- Fix: use a defined JSON Schema validator or explicitly support a narrow schema dialect and reject all unsupported keywords/types at registration. Add enum/range/nested-array regressions.
- Confidence: verified; existing schema test verifies only wrong primitive type and duplicate tool registration.

This is a dry-run event viewer, not deterministic replay of agent decisions or evidence of trace completeness. Current replay test only asserts `side_effects_applied=False`.

#### W1 — High: approved in-workspace patch can overwrite a file outside the workspace

- Mechanism: CaseResult stores id/type/output/status/check/latency/error only. Prompt, context, generation settings and case metadata are absent. Report.configuration contains only seed.
- Synthetic evidence: case snapshot keys were ['case_id','check','error','latency_ms','output','status','task_type']; configuration was {'seed':1337}.
- Impact: the suite fingerprint detects changed input but cannot reconstruct it; replay/comparison depends on retaining an unchanged external suite. “Complete case snapshots” is stronger than the implementation.
- Fix: store the normalized case and effective generation options, with an explicit private-data/redaction policy; narrow documentation until implemented.
- Confidence: high. Existing tests assert output/failure counts, not snapshot completeness.

#### EV6 — P2 confirmed: invalid generation settings abort the whole evaluation

- Source: src/nanoforge/evaluation/suite.py:255; :108; :221.
- Mechanism: max_new_tokens int conversion occurs outside per-case try/except. Loader validates generation only as a dict. Unknown sampling keys are silently filtered.
- Synthetic evidence: a suite with a valid first case and a second max_new_tokens='bad' raised ValueError instead of returning a report with a visible error case.
- Impact: one malformed option prevents report writing and loses results from already-run cases; misspelled settings can change the experiment silently.
- Fix: validate case option schemas before execution and record case errors explicitly where execution is permitted; reject or report unknown keys.
- Confidence: high; silent-key issue is source-verified.

#### EV7 — P2 confirmed: distinct report filenames overwrite one another's case sidecars

- Source: src/nanoforge/evaluation/suite.py:317.
- Mechanism: every report in a directory writes fixed cases.jsonl and failures.jsonl regardless of the report filename.
- Synthetic evidence: write a.json for case A, then b.json for case B; a.json still contains A but its returned cases sidecar contains B.
- Impact: valid CLI output-file usage produces mismatched all-case/failure artifacts and can invalidate downstream comparisons.
- Fix: put each run in its own directory or derive companion filenames from the report stem; save the report/sidecars as one generation.
- Confidence: high. Existing tests use one report per directory.

#### EV8 — P2 confirmed: profile-config ignores selected model architecture

- Source: src/nanoforge/profiling.py:34.
- Mechanism: fixed dense three-matrix FFN formula ignores MoE experts/router, actual rounded hidden size, alternative heads/norms and LoRA.
- Synthetic evidence: tiny dense config estimated/actual 28,768/28,768 parameters; same config with four experts estimated 28,768 versus actual 77,984. d_model=256 dense example estimated 1,607,424 versus actual 1,737,984 because construction rounds FFN width. Sequence classification example estimated 32,864 versus actual 29,890.
- Impact: parameter and optimizer memory reports can materially mislead hardware selection. Formula-based activation/optimizer figures are estimates, not measured peak memory.
- Fix: derive parameter counts from actual selected components or architecture-aware formulas; label assumptions and use empirical peak measurements separately.
- Confidence: high. Existing profile test checks positivity only.

#### EV9 — P2 static / inaccurate claim: RAG building retains the corpus and dense vectors in RAM

- Source: src/nanoforge/rag/store.py:113, :145 and :86; src/nanoforge/rag/indexer.py:3.
- Mechanism: every chunk text is retained in docs, every embedding batch in vec_batches, then np.vstack(...).astype(float32) copies the complete matrix. Loading also copies np.load output via astype.
- Source-derived scale, not a measured production benchmark: 100,000 default 16,384-dimensional float32 vectors require about 6.10 GiB per matrix; stacked/cast allocations add multiples of this, plus text/metadata.
- Impact: streaming input does not mean bounded-memory indexing. The module statement that nothing loads a full corpus into RAM is false for stored chunks.
- Fix: append vectors to mmap/shards, stream metadata to disk, bound the TF-IDF fit sample, and document dense-index limits.
- Additional static integrity gap at store.py:158: three individually atomic file replacements are not an atomic index transaction; a crash between replacements or concurrent writes with fixed .tmp names can leave mixed generations. Loader does not validate vector/doc/meta counts or dimensions.
- Confidence: high for memory mechanism; concurrency/crash exposure is source-verified, not reproduced.

#### EV10 — P3 confirmed: explicit legacy schema zero is not migrated to current version

- Source: src/nanoforge/artifacts.py:164.
- Mechanism: migrate_manifest uses setdefault('schema_version',1), so an explicitly supplied zero remains zero after defaults are added.
- Synthetic evidence: migrate_manifest({'schema_version':0})['schema_version'] returned 0.
- Impact: a load/write roundtrip continues labeling migrated output as legacy; schema migration is incomplete.
- Fix: validate supported nonnegative integer versions and assign the new version after migration.
- Confidence: high. Existing tests cover absent manifests and future-version rejection, not explicit version-zero roundtrips.

### What problem Nanoforge should solve

**A developer with an ordinary workstation should be able to use a capable local model to make a small repository change, approve its effects, run a fixed test profile, and verify exactly what changed without sending the repository elsewhere.**

This is narrower than creating broad intelligence from scratch and matches the charter. Coding gives executable feedback; local data/privacy and reproducible approval/evaluation are the differentiators. The compact scratch stack remains a useful educational/research lane. The first product should compose an existing quantized coding model with the harness; adaptation should follow only after a measured retrieval/behavior gap.

#### Smallest complete next slice

1. Fix release/privacy blockers and runnable synthetic examples; expose truthful current-vs-target capability status.
2. Select one licensed local GGUF coding model through a versioned project manifest; preserve tokenizer/chat/action identity.
3. Implement one tested model → action adapter and bounded read context. Use allowlisted repository tools.
4. Show a concrete diff and explicit write/test approval in the TUI; execute tests in an actual isolated process boundary; provide timeout and cancellation.
5. Persist a redacted trace and immutable run manifest; replay without effects.
6. Evaluate a small public synthetic/held-out repair suite, including stale patches, denied approvals, bad paths, model-invalid output, test failure/recovery, context overflow and cancellation.

**Acceptance:** from a clean install, one command opens the project; one model-driven held-out repair produces an approved tested patch or an explicit bounded failure; no unauthorized write/test/network occurs; replay changes no files; failures remain inspectable; report task pass rate, TTFT, tokens/sec, peak RSS/VRAM and artifact identities. Set numeric budgets only after measuring the fixed hardware/model baseline.

**Defer:** more exotic attention architectures, general personal memory, arbitrary shell/network tools, public multi-user serving, and from-scratch broad-model training until this slice delivers repeatable user value.
